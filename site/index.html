the four invisible classes

Losses nobody counts

Every hop in a log pipeline can drop data, and each hop's self-reporting covers only the failure modes its authors anticipated. These four recur across vendors and years.

01

Discovery races

A short-lived pod writes and exits before the agent's file-discovery interval fires. The file is gone before anything tailed it, and no counter anywhere moves.

02

Rotation races

A file rotates while the agent is mid-read. Lines in the gap window vanish. Under load, records get split or dropped with nothing recording it.

03

Semantic drops

The source deliberately skips data it considers invalid. A line whose timestamp precedes the previous one, for instance, which stdout and stderr interleaving triggers constantly. The source does not call this an error, so nothing is logged.

04

Ingest rejections

The store rejects a document for a mapping conflict, malformed JSON or an oversized line, after the agent already counted it as delivered.

the honest boundary

Nothing reaches into your pipeline

The emitter is only another log producer. The verifier is only another query client. The canary travels the same path your application's logs do, so every gap it finds is one they would have hit too.

documented, not hypothetical

The counters lied, and someone measured it

All four are public reports. In every one, the in and out counters agreed while logs went missing.

grafana/alloy #7076 A user-run canary measured entries silently dropped over 14 hours because out-of-order timestamp lines were discarded. Zero errors reported anywhere. 199 of 5,035 lost
fluent-bit #2509, #2955 Pods silently stopped shipping for hours. "I didn't find any errors in fluent bit as well as elasticsearch." In and out counters matched throughout. hours, unnoticed
Elastic Discuss Filebeat to Logstash to Elasticsearch losing logs "often and sometimes in a massive way", while Logstash in, filtered and out stats were "almost the same". counters agreed
UK MoJ Cloud Platform The log store stopped receiving. A human noticed via Slack about 40 minutes later. The incident runbook closes with a single line. "not recovered"

Four organisations independently built this harness internally: AWS runs release-blocking log-loss tests, Grafana built loki-canary, VictoriaMetrics built log-verifier, OpenTelemetry has an open request for it. None of them ships a generic, multi-collector, real-store version, because a neutral cross-vendor auditor belongs to nobody's roadmap.

an accusation is earned twice

Four gates before we call anything lost

A pipeline is asynchronous. At any instant some lines are legitimately in flight. Calling those lost would be a false accusation, which is worse than a missed detection, because it destroys the credibility that makes detection worth reporting.

01

Within the epoch

At or below the epoch's expected high-water mark. A crashed emitter truncates the epoch, so nothing past its last written sequence can be called lost.

02

Absent from the sink

Queried directly from the store. Collector self-reports are never used as verdict input. A component only counts the drops it notices.

03

Past the settle window

An adaptive delay per sink. Both inputs push the window outward only, so lengthening it can never create a new accusation.

04

Confirmed by a re-check

A mandatory second query. Only a sequence that survives all four is reported missing, with exact ranges rather than a total.

lossledger_false_missing_total

Counts sequences this verifier declared missing that later arrived. It is the shame counter, exported from day one and printed on every report whether it is zero or not.

A nonzero value means the harness accused a pipeline of losing data it went on to deliver. That is a bug in LossLedger, not in your pipeline, and it outranks every feature. You cannot publish a result from this tool without publishing this number beside it.

what auditing costs

Expensive queries scale with loss, not with traffic

Listing 173 million sequences a day would cost more than the pipeline being audited. So the verifier asks one wide question first, and only looks closer where the answer disagrees.

severity is the interface

Five verdicts, ordered

The same ordering drives exit codes, CI budgets, report sorting and alert levels. A harness error exits 2, below every anomaly, so a crash can never be mistaken for a finding.

VerdictMeaningExit
MISSINGAbsent after the settle window and a mandatory re-check. Exact ranges reported.40
DUP_BUGDuplication outside any replay window, or past the duplication factor bound.30
ORDERArrival order violated sequence order, or a multi-line event arrived partially.20

DUP_REPLAYExpected at-least-once duplicate after a restart. Informational, never a failure.0

try it in a minute

Prove the harness before trusting it

Two reference collectors ship in-tree. One copies faithfully and must come back clean. The other drops a known range, duplicates another and truncates multi-line events, and must be caught with exactly those ranges.

git clone https://github.com/Vishv07/Lossledger # Build the binary. go build -o lossledger ./cmd/lossledger export LOSSLEDGER_HMAC_KEY="any-shared-secret" # Emit and verify against a directory acting as a store. ./lossledger run -dir /tmp/canary -count 1000 # Then grade the harness itself against the reference pipelines. ./lossledger selfcheck # [PASS] refbad missing ranges match the injected drops exactly # [PASS] refbad integrity metric is zero # 14 of 14 checks passed

If that gate fails, nothing the build says about a real pipeline is worth reading. It runs in CI on every commit, and any change that flips it blocks the merge.

Who this is not for

Most teams tolerate one to two percent log loss without noticing, because most log lines are never read. This is a tool for teams where logs are legally or contractually load-bearing, for platform teams who already build this internally, and for engineers mid-incident who just found the missing line. Thousands of deployments, not hundreds of thousands.

  • Logs only. No metrics, no traces.
  • Attribution is source-side versus sink-side only. Per-hop attribution across a broker is v2.
  • Linux is the target. The Go code is portable, but fault injection and journald are not.
  • No remediation. LossLedger proves loss, it does not repair it.
  • Canary lines cost money in billed stores. One node at 10 lines per second produces roughly 864,000 lines a day.
  • A clean result means this pipeline delivered these canaries under these conditions. It is not a proof that nothing is ever lost.
